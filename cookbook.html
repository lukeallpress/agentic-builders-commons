Google sign-in & Firebase
LA

One small login app holds the district's only OAuth redirect and issues a shared cookie carrying identity ONLY — every app re-resolves roles from the database per request, so revoking access takes effect on the next click. 11 apps on it.

AM

Google-side auth (Firebase / Google) in front of her Google Cloud tooling.

RG

Runs Google Firebase in his stack alongside Google Cloud and AWS.

GS

Puts his idea-catcher portal behind Google SSO so submissions stay internal to district staff.

GR

Ties the district AI chat platform to Google Workspace for role-based access across staff and students.

HP

Google OAuth in front of a Supabase role/permission model with row-level security.

Commentary from the folks above lands here as members annotate the cookbook.

Active Directory for access control
LA

Google answers "who are you"; Active Directory governs what you may see. Never put roles in the shared cookie — identity in the cookie, authorization re-resolved from the database on every request.

Commentary from the folks above lands here as members annotate the cookbook.

Delegated agent accounts
KH

Every agent gets its own delegated Google Workspace account, scoped like the staff member it assists — agents never borrow a human's credentials. Proven in the OpenClaw executive-cabinet rollout.

Warehouse + MCP access layer
KH

A Python MCP server sits between agents and the warehouse (Redshift / PostgreSQL, PowerSchool) and enforces role-based access — a principal's agent only retrieves that principal's building. Agents ask approved tools; nothing queries production directly.

JN

Connects agents to Google Workspace and his Zoho CRM through MCP servers; a master course database lives in Obsidian, with Markitdown parsing documents on the way in.

MP

A Data MCP that limits results by the authenticated caller's role, now feeding live Atrium dashboards — plus write tools for OneSync and Roster Server so rules can be changed by asking rather than by hand.

RH

Reverse-engineers vendor CLIs and APIs to reach data the district already pays for when the vendor offers no interface.

Direct SIS pulls into a district warehouse
LA

An IP-whitelisted server reaches the SIS database directly, and nightly / hourly exports land in a local Microsoft SQL Server that hosts all district data. Agents reach it only through an MCP server whose stored procedures re-resolve the caller's scope on every call.
